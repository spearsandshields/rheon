# Identity of full responses against the previous release

The released module is the frozen oracle of today's behaviour. Every request of the committed
sources goes through it and through a candidate build, and every full response (result, type,
warnings, diagnostics, errors, traps) must be identical, except the differences registered in
`registered/`. A change that alters an answer therefore names it, with its basis and both answers,
in the commit that makes it.

```sh
bash tools/identity/fetch-baseline.sh               # .tools/baseline/feel.wasm, the release in baseline.json
npm run build:wasm                                  # dist/feel.wasm, the candidate
bash tools/identity/run.sh .tools/baseline/feel.wasm dist/feel.wasm [source…] [option…]
```

`npm run identity` runs the first and the last command, `npm run identity:large` the same with
`--large`; arguments after `--` are passed on to `run.sh`.

The test tiers run the check after the wasm build (`scripts/tier.mjs`, README "Test tiers"): the
fix and group tiers on the committed sources, the release tier also with `--release` and
`--large`; the group tier also runs `npm run test:identity`. CI runs the group tier with
`GH_TOKEN` set to the workflow's token for the download.

The committed request sources are `requests/` and `wasm/feel-wasm/tests/corpus/no-trap.json`, and
`release/requests/` with `--release`. A request of `release/requests/` is left out of every other
source when `--release` is not given (`equal.mjs --exclude`), and its ledger entry belongs in
`release/registered/`, so that no run without `--release` evaluates it. A
source is a JSON file holding one request or an array of requests, exactly as a host sends them, or
a directory of such files. Each request is sent byte for byte as it is written in its file, and so
is the `request` of a ledger entry. `run.sh` also sends every `evaluate` request as a `parse`
request, the same request with `op` set to `"parse"`. Requests that call `now()` or `today()` are
left out, because their answers depend on the clock.

JSON is read losslessly: a number keeps its source text in requests, responses and ledger
entries, so a number beyond the range or precision of a double (`1.5e-6176`, a 1,000-digit
integer) is sent, keyed and compared exactly as written. This needs Node 21 or later
(`JSON.rawJSON` and the source text of a parsed number); an older Node exits with status 2.

With 0.5.0 as the reference, Node 21 or later is enough: no committed request makes it crash
Node, and a request that exhausts its memory, such as those of `release/requests/`, ends as a
trap of the module (`docs/FORK.md` records that Node 22 reports such a trap as well). A run whose
reference is 0.4.0 or older, such as a bisect of older commits or a comparison with an old
release, needs Node 24 or later: the request
`{big: for i in 1..100000 return i, r: for j in 1..1000 return big = j}.r` makes the 0.4.0 module
exhaust its memory, which Node 24 and Node 26 report as a trap of the module, while Node 22.23
crashes itself with a segmentation fault (6 of 6 runs, macOS arm64 and the ubuntu runner), so the
run ends with status 139 before it compares anything. CI runs Node 24, the version its times are
measured on; the times below are of Node 26.

## While developing

| When | What | Time |
|---|---|---|
| After every build (the fix and group tiers) | `npm run identity`: the committed sources | 4.5 s uncached, 2.8 s cached |
| Once per group of changes, on demand | `npm run identity:large`: the same with the larger request sets kept outside the repository (`IDENTITY_LARGE_SETS`) | 38 s uncached, 20 s cached |
| On a failure | `--record <entries.json> --why "<basis>"`, then `git bisect start <bad> <good>` and `git bisect run tools/identity/bisect.sh .tools/baseline/feel.wasm <entries.json>` | one wasm build per step |
| Before a release (the release tier) | `run.sh … --release --verify-cache` and `run.sh … --large --verify-cache` | 7.8 min (measured without `--verify-cache`) and 39 s |

Measured on a MacBook (Apple M2, Node 26) against 0.5.0, with every evaluate request also sent as
parse: the committed sources are 12,916 requests, with the two sets kept outside the repository
13,109 (the 33 of `release/requests/` and their parse twins left out, 44 in all), and with
`--release` 12,980.
Four committed requests trap 0.5.0: the loops of `registered/abort-stops-loops.json`, which ran
on after an abort until they exhausted its memory (0.4 s each), and the two `context put` with a
list of 100,000 keys of `registered/value-depth.json` (14 ms each). Nine requests of the large
sets, depth probes 501 levels deep, answer the value-depth error, while 0.5.0 answers seven of
them and traps on two (one of them a context literal of 100,000 entries that each nest the one
before, which the candidate also exhausted its memory on before contexts were shared); they are not committed, so they are not registered, and `--large` lists them
as differences. Five requests of the large sets trap 0.5.0 (two of them after 1.2 s each, three
at once); the 17 of `memory-exhausting.json` exhaust its memory (1.2 to 1.7 s each, its two
100,000-level loops after 158 s and 35 s), and the candidate answers 12 of them (the two loops
with the value-depth error, the 7 of `release/registered/shared-lists.json` in 7 to 9 ms
each, and the 3 of `release/registered/shared-contexts.json`: in 8 ms, 1.6 ms and 0.4 ms) and exhausts its memory on 5; the 12 of `values-deep.json` take
44 s on each side, and the 4 of `value-depth-deep.json` trap the reference after 0.6 to 1.3 s. The
release run took 528 s (peak 4.9 GB). A cached trap is evaluated again on every run (see the
cache section), so the cache cannot save that time. The peak memory is 3.4 GB for the large sets
(20 s cached) and for the release sources (4.1 GB with `--verify-cache`, measured before
`values-deep.json` was added). The uncached time of the large sets and the time of
`--large --verify-cache` are of the runs before `values.json`, `values-deep.json`,
`value-depth.json` and the requests of `abort-stops-loops.json` were added.

`bisect.sh` builds `dist/feel.wasm` of the checked-out commit and passes the entries as the only
ledger: a commit that answers every entry's `new` is bad (exit 1), any other is good (exit 0), and
a failed build or an input error skips the commit (exit 125). When the entries come from several
changes, the bisect ends at the last of them; cut the file to the entries that commit does not
explain and bisect again. The script uses the `equal.mjs` next to it, so to bisect commits older
than the script, run a copy of `tools/identity/` and `scripts/feel-abi.mjs` kept outside the work
tree in the same layout. With a third argument it checks that module instead of building one.

## Comparison rules

1. `elapsedMicros` and `engineCommit` are removed from every response, and `version` from `info`
   responses. A trap of the instance is the response `{"trap": true}`, and the next request runs on
   a fresh instance. The reference answers each source file (with the parse twins of its requests)
   and each ledger file on a fresh instance of its own, so that its answers to a file depend on
   the module and the file alone; a request that several files list takes the answer of the first.
   The candidate answers every request once, on one instance.
2. Every request is compared. A difference that is neither registered nor explained by a rule
   entry fails the run.
3. Every ledger entry and every example of a rule entry is run, whether or not a source lists its
   request. The reference must answer its `old` and the candidate its `new`; an entry or an
   example that does not reproduce fails the run, so the ledger cannot go stale.
4. A request is registered at most once across all ledger files, as an entry or as an example.
   Its key is its JSON with sorted object keys.
5. A request with an entry of its own is checked against that entry only. A difference of any
   other request is explained by the first rule entry, in ledger order (files by name, entries in
   file order), that it is an instance of; a difference that no rule explains fails the run.
6. A response that is not JSON fails the run.
7. Exit status: 0 when every response is identical, registered or explained, 1 on any failure, 2
   on a usage or input error (including a malformed ledger).

## The cache of reference answers

The reference is a fixed module, so its answers to a file do not change until the file does.
`--cache <dir>` keeps them, one file per source file or ledger file, and `run.sh` passes
`--cache .tools/identity-cache` (git-ignored, under `.tools/`). The candidate is never cached.

- A cache file is `<dir>/<sha256 of the reference module>/<16 hex digits of the sha256 of the
  unit's absolute path>-<file name>.jsonl`: a header line, one line per request of the unit (the
  sha256 of the request text sent, and the answer as the canonical text of the response without
  the fields of rule 1, or `"trap": true`), and a trailer line with the sha256 of every byte before
  it.
- The cached answers are used only when the trailer's digest is right and the header equals the
  run's: the format, the reference's sha256, the sha256 of the unit file's bytes, the kind of unit
  (requests or ledger), `--parse-too`, the sha256 of `equal.mjs`, `json.mjs`, `rules.mjs` and
  `scripts/feel-abi.mjs`, and
  Node's version, architecture and `execArgv`; the request hashes must also be the unit's requests
  in order. Anything else is a miss: the unit is evaluated and its file written again (to a
  temporary file, then renamed). An existing file that does not match is reported as
  `cache: <file> rejected (<reason>), evaluating`.
- A trap depends on the host as well as on the module (stack and memory limits), so every cached
  trap is evaluated again, on a fresh instance each. If it answers, the file is rejected and the
  unit evaluated in full. A ledger entry with `"old": {"trap": true}` is therefore proven on every
  run.
- A unit with a response that is not JSON is not cached; the run fails as without a cache.
- There is at most one file per unit path, and a new reference directory removes the directories
  of other references, so the cache holds no more than one file for each file a run has named
  with the current reference. It holds no engine state, and deleting it is always safe.
- The summary line ends with `reference: <n> answers from the cache, <m> evaluated`.
- `--verify-cache` evaluates the reference in full, compares every answer of a matching cache file
  with the live one, reports each difference as `CACHE MISMATCH <request>` (exit status 1) and
  writes the files again. Run it over every request set before a release.
- CI starts from a fresh checkout and restores no cache, so its run is uncached.

## Ledger entries

A ledger file is a JSON array of entries:

```jsonc
{
  "expression": "string(time(\"10:00:00.0157\"))",  // or "request": { the whole request }; "expression" stands for {"op": "evaluate", "expression": …}
  "why": "DMN 1.6 §10.3.2.3.4: …",                  // the clause or the documented rule the new answer follows
  "old": "10:00:00.015699999",                      // what the reference answers
  "new": "10:00:00.0157"                            // what the candidate answers
}
```

`old` and `new` take one of these forms, and `old` must differ from `new`:

- A string, in both: the result text, that is `result.display` without its JSON quotes when
  `result.type` is `string`. Both responses must succeed, and they must agree on `ok`,
  `result.type`, `warnings` and `diagnostics`.
- An object: the whole response, without the fields of rule 1.
- `{"trap": true}`: the instance traps.
- `{"sha256": "<64 lowercase hex digits>"}`: the whole response, without the fields of rule 1, by
  the sha256 of its canonical text (the text the cache stores). It keeps a ledger small where a
  response is long, such as the rendering of a value nested 500 levels deep.

`why` is timeless and self-contained: it states the basis, not a plan or a tracker. Draft a file
with `run.sh … --record <out.json> --why "<basis>"`, which writes the run's unregistered
differences as entries in the whole-response form, a response longer than 65,536 characters as
its digest; then check every `new` against the spec before committing it.

## Rule entries

A rule entry explains a class of differences that many requests share, such as diagnostics that a
change no longer records, instead of one entry per request. It stands in a ledger file beside the
request entries:

```jsonc
{
  "rule": "right-operand-not-evaluated",           // a name of lowercase words joined by hyphens, unique in the ledger
  "why": "DMN 1.6 §…: …",                          // the basis, as for a request entry
  "applies": { "expression": "\\b(and|or)\\b" },   // optional: the rule explains only requests whose expression matches
  "allow": [                                       // the paths where the two responses may differ, each once
    { "at": "diagnostics.count", "change": "decreases" },
    { "at": "diagnostics.messages", "change": "loses", "each": "^\\[addition\\] " }
  ],
  "examples": [                                    // at least one, each in the whole-response form
    { "expression": "false and (1 + \"a\")", "old": { … }, "new": { … } }
  ]
}
```

A path names a field by its keys joined with dots (`diagnostics.count`, `result.display`); a key
ending in `[*]` stands for each element of two arrays of equal length (`warnings[*].message`). An
absent field counts as 0 for `decreases` and `increases` and as the empty list for `gains` and
`loses`. The changes:

- `gains`: both lists, the old one a subsequence of the new one, and every added element matching
  the regular expression `each` (required); an element is matched as its text when it is a string,
  otherwise as its canonical JSON;
- `loses`: the mirror image, `each` matching every element the new list drops;
- `decreases` and `increases`: both JSON integers, compared exactly from their source text, and
  the new one strictly smaller or larger;
- `rewrite`: both strings, and the old text with every match of `pattern` replaced by
  `replacement` (JavaScript's `String.replace`, so `$1` names a group) is the new text.

A difference is explained when both answers are responses (a trap is never explained), the two
values at every allowed path stand in its relation, and the two responses are identical once the
allowed paths are removed; an object that the removal leaves empty is removed with them, so
`diagnostics` that a change drops entirely compares equal to its absence. Anything else stays a
difference. A transformation that a regular expression cannot state is added to `rules.mjs` as a
named change, with the first change that needs it.

Each example is a ledger request like any other: the reference must answer its `old` and the
candidate its `new`, so a rule whose examples no longer reproduce fails the run. An example must
be an instance of its rule and match its `applies`, and a malformed rule is an input error (exit
status 2). The summary line counts the explained differences per rule, `--explained <out.json>`
writes every explained request with its rule's name and both answers for review, and `--record`
writes only the differences that nothing explains.

## When a release is cut

The commit after the release tag moves `baseline.json` to the new release (`tag` and the `sha256`
of its `feel.wasm` asset) and deletes `registered/*.json` and `release/registered/*.json`: the new
release answers every request as registered. A request of `release/requests/` that the new release
answers in well under a second moves to `requests/`. Git history keeps the old ledger, and `docs/FORK.md` keeps the count of registered
differences per change.
